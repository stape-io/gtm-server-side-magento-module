# Issue tracker: Jira

Jira is the only issue tracker: `stape.atlassian.net`, project `DEV`, reached through the Atlassian MCP (`cloudId`: `stape.atlassian.net`). Operations below are named by what they do; use the matching tool of the connected Atlassian server, and its `discover` tool for operations outside your tool list (issue links, transitions, page descendants). A search for duplicates or a queue asks for the fields it needs (`summary`, `status`) and 10–20 results; by default some servers return every description. With no Atlassian MCP connected, stop and say so: the plugin does not ship one, and `/stape-dev:setup` says how to connect it. These sections stand in for `/setup-matt-pocock-skills`, which this plugin does not ship.

A ticket is a **standalone artifact**, read by people outside the repo: explain the change in product terms, with repo paths only as supporting detail. Prose that people read (a ticket, a spec, a PR body, a Confluence page) goes through `/stape-dev:unslop` before it is published.

**Estimates follow the ticket's birth.** When `triage` marks a ticket `ready-for-agent` or `ready-for-human`, or `to-tickets` publishes tickets, run `/stape-dev:estimate` on them (an Epic estimates all its unestimated children in one table); nothing is written before the user confirms. Bugs get points too; sub-tasks and sub-bugs never do, so they get no estimate and no nudge.

"Publish to the issue tracker" means: a spec → `Epic`; implementation work → `Backend Task` / `Frontend Task`; a question → `Spike`. Blocking edges are `Blocks` links, the inward issue being the blocker. **Confluence is input**: a page handed to a skill is source material, linked from the map's Notes or the spec's Further Notes; decisions and specs live in Jira.

**Ticket status.** The workflow is Backlog → To Do → In Progress → In Review → Ready For Testing → Testing → Waiting For Release → Done. Taking a ticket to work on it: assign it to the user and transition it to **In Progress**. A ticket that takes points goes there with them: with Story Points empty, run `/stape-dev:estimate` first. Opening its PR: transition it to **In Review**. Pick a transition by the status it leads to, not by its name: list the issue's transitions and take the available one into that status (into In Review it is `to Review`). When a ticket stays without points (the user declines the estimate, or `estimate` skips it as untriaged) or Jira refuses a transition, leave the ticket where it is, tell the user why, and go on with the work. Later statuses belong to QA and release; work closes through the PR, so a ticket is never moved to Done by hand.
